# ZTE MF для Home Assistant

Локальна custom integration для модемів ZTE серії MF з налаштуванням через UI.
Початкова модель — **ZTE MF920U**, профіль — **BD_CNCNLMF920UV1.0.0B10**.
Моделі та варіанти API додаються окремими профілями.

## Можливості

- Адреса, модель, профіль прошивки та пароль налаштовуються через UI.
- Автовизначення відомої прошивки або явний вибір профілю.
- Переналаштування адреси/профілю й повторна авторизація при зміні пароля.
- Окрема cookie-сесія для кожного модему; відновлення після завершення сесії.
- Опитування раз на 30 секунд, налаштовується в межах 10–3600 секунд.
- Стабільний ідентифікатор пристрою за IMEI або MAC, незалежний від IP/SIM.
- Українська й англійська мови форми.

| Сутності | Показники |
| --- | --- |
| Мережа | Оператор, тип мережі, стан SIM, мобільне з’єднання, роумінг |
| Сигнал | Поділки сигналу, RSSI, RSCP, LTE RSRP |
| Живлення | Заряд батареї, заряджання |
| Трафік | Передані/отримані байти за сесію, швидкості в B/s, тривалість з’єднання |

Відсутні/некоректні показники стають `unknown`, при втраті зв’язку сутності —
`unavailable`. Лічильники трафіку можуть скидатися після перепідключення.
RSSI/RSCP/RSRP залежать від типу мережі й прошивки.
Інтеграція читає телеметрію; єдина POST-операція — вхід у вебінтерфейс.

## Сумісність

Потрібен Home Assistant **2025.1+** і мережевий доступ від HA до модему.
На `192.168.0.1` перевірено доступність Goform API та рядок прошивки;
команди й алгоритм входу звірено з JavaScript вебінтерфейсу пристрою.
Без авторизації показники порожні. Повний вхід і живу телеметрію потрібно
перевірити з вашим паролем після встановлення. HTTP-тести імітують відповіді
модему; HA-тести запускають справжній тестовий runtime Home Assistant.

Наразі у списку моделей лише MF920U. Неперевірені моделі не позначено підтримуваними.
`Automatic` приймає точний відомий рядок прошивки. Ручний вибір застосовує профіль
незалежно від рядка версії, що дозволяє перевіряти сумісні модифікації, але не
гарантує їхню підтримку. Інтеграція не змінює прошивку модему.

## Встановлення

### Вручну / з develop

1. Скопіюйте `custom_components/zte_mf` у `/config/custom_components/zte_mf` на HA.
   Або розпакуйте ZIP із GitHub Release в `/config`: він уже містить цей шлях.
2. Перезапустіть Home Assistant.
3. **Налаштування → Пристрої та служби → Додати інтеграцію → ZTE MF**.
4. Вкажіть `192.168.0.1`, `MF920U`, `Automatic` або профіль B10 та пароль
   **вебінтерфейсу модему** (не Wi-Fi і не PIN SIM).

YAML не потрібен. Адреса може містити `http://` / `https://` та порт.
Для зміни адреси/профілю/пароля використовуйте **Переналаштувати** в меню інтеграції.
Порожній пароль під час переналаштування зберігає попередній.
Для іншого фізичного модему додайте нову інтеграцію.

### HACS

Додайте `https://github.com/goblinmaks/zte-mf-home-assistant` як custom repository
типу **Integration**, встановіть ZTE MF і перезапустіть HA. Це не означає включення
до стандартного каталогу HACS. HACS використовуйте після першого релізу з `main`;
для поточної гілки `develop` доступне ручне копіювання.

Пароль зберігається в config entry HA; не додавайте його в Git або issue.
Ця прошивка використовує Base64 через HTTP. Base64 не шифрує пароль, тому
вебінтерфейс має бути доступний у довіреній локальній мережі.
Після відхиленого пароля HA запропонує повторну авторизацію без циклічних спроб входу.

## Додавання моделей і прошивок

Реєстр — `custom_components/zte_mf/profiles.py`:

1. Перевірте запити вебінтерфейсу нової моделі, назви полів, одиниці та спосіб входу.
2. Додайте `FirmwareProfile` у `PROFILES` зі стабільним ключем, моделлю і точним
   рядком версії. Переліки моделей/профілів у UI формуються автоматично.
3. Для іншої авторизації додайте стратегію до `api.py`. Наразі реалізовано лише
   Base64 LOGIN; SHA/challenge-вхід не заявлено підтримуваним.
4. Якщо поля/одиниці відрізняються, додайте нормалізацію до канонічних полів
   сенсорів у профілі/клієнті та тести.
5. Додайте знеособлені приклади відповідей і перевірки перед оголошенням підтримки.

Профілі містять шляхи API, команду входу, кодування та список команд опитування.
Розширення не потребує зміни форми вибору моделі/прошивки.

## Розробка

```sh
python -m venv .venv
# Linux/macOS: source .venv/bin/activate
# Windows: .venv\Scripts\Activate.ps1
pip install -r requirements-dev.txt
ruff check .
ruff format --check .
pytest tests/unit
python scripts/validate.py
python scripts/package.py
```

HA-тести запускайте в окремому Linux-середовищі Python 3.14:

Тестова залежність зафіксована для Home Assistant 2026.9.4.

```sh
pip install -r requirements-ha-test.txt
pytest tests/ha
```

Unit-тести перевіряють HTTP/JSON, IP cookies, повторний вхід, помилки, адреси
та профілі. HA-тести перевіряють форми, дублікати, reauth, сутності, options та unload.
CI виконує ці перевірки та Hassfest для push/PR у `develop` і `main`.

## GitHub CI/CD і версії

Розробка — у `develop`, перенесення до `main` — через PR. Release workflow працює
лише для `main`, включно з ручним запуском, і залежить від успішного CI.
Використовуйте Conventional Commits у squash-заголовках PR:

- `fix: ...` — patch;
- `feat: ...` — minor;
- `feat!: ...` / `BREAKING CHANGE:` — несумісна зміна (до 1.0 — minor).

Release Please автоматично створює release PR до `main` із `CHANGELOG.md`,
`version.txt`, `.release-please-manifest.json` та версією у `manifest.json`.
Після його злиття створюються тег `vX.Y.Z`, GitHub Release і ZIP із тегованого коду.
Початкова версія коду — `0.1.0`; кожен push у `develop` не створює новий реліз.
Злиття release PR є явним кроком затвердження релізу.

У GitHub **Settings → Actions → General → Workflow permissions** дозвольте
створення PR через GitHub Actions. Права `contents: write` та `pull-requests: write`
надаються лише релізному job. Зазвичай достатньо `GITHUB_TOKEN`.
PR від цього токена не запускає нові workflows автоматично: якщо branch protection
вимагає PR-checks, запустіть CI вручну для гілки release PR або налаштуйте GitHub App
token для Release Please. Перед фактичним релізом CI все одно виконується на `main`.
Після релізу синхронізуйте `main` назад у `develop`.
